## 1. Architectural Summary & Scope

The **Alerts Module** (`apps.alerts`) provides a secure, read-only RESTful API layer for inspecting historical alert notifications and hazard dispatches generated by the computer vision detection engine.

### Key Architectural Decisions:
1. **Model Reuse & Zero New Migrations**: Reuses the existing `Alert` model (`apps.alerts.models.Alert`) linked via foreign key to `apps.detection.models.AnimalLog`. Zero database schema modifications or migrations were created.
2. **Immutable Historical Audit Trail**: Alerts represent immutable historical notification events triggered during animal hazard detection. The API is strictly read-only (`GET` list and `GET` detail). Mutation methods (`POST`, `PUT`, `PATCH`, `DELETE`) return `HTTP 405 Method Not Allowed`.
3. **Seamless Step 10 Detection Integration**: Automatically exposes alerts created by `DetectionService.analyze_image_bytes` and real-time streaming inference pipelines.
4. **Structured Context Serialization**: Flattens associated animal detection details (`animal_type`, `confidence`, `field`, `image_path`, `detection_timestamp`) into alert responses without circular references or data leakage.
5. **Standardized Response Envelopes**: All responses strictly adhere to FarmSync's `{ "success": true, "message": "...", "data": ... }` contract.

## 3. Endpoints Reference

Base path: `/api/v1/alerts/`

| Method | Endpoint | Authorization | Description | Classification |
| :--- | :--- | :--- | :--- | :--- |
| `GET` | `/api/v1/alerts/` | Authenticated | Lists all alert notification records with optional filtering (`status`, `alert_type`, `animal_log_id`, `animal_type`, `date`, `start_date`, `end_date`) ordered by `-created_at`, `-id`. | **LEGACY-VERIFIED & ENHANCED** |
| `GET` | `/api/v1/alerts/{id}/` | Authenticated | Retrieves detailed record of a single alert event including associated animal detection context. | **NEW DJANGO ENHANCEMENT** |
| `POST` | `/api/v1/alerts/` | — | Method Not Allowed (HTTP 405). Alerts are created exclusively by the detection pipeline. | **AUDIT SAFETY RULE** |
| `PUT` | `/api/v1/alerts/{id}/` | — | Method Not Allowed (HTTP 405). Alerts are immutable historical records. | **AUDIT SAFETY RULE** |
| `PATCH` | `/api/v1/alerts/{id}/` | — | Method Not Allowed (HTTP 405). Alerts are immutable historical records. | **AUDIT SAFETY RULE** |
| `DELETE` | `/api/v1/alerts/{id}/` | — | Method Not Allowed (HTTP 405). Alerts cannot be deleted via API. | **AUDIT SAFETY RULE** |

## 5. Security & Validation

- **Authentication Required**: All endpoints reject unauthenticated requests with `HTTP 401 Unauthorized`.
- **Query Parameter Validation**: Strict validation via `AlertFilterSerializer`. Malformed date formats (`?date=invalid`), inverted date ranges (`start_date > end_date`), or unsupported status/type choices return `HTTP 400 Bad Request`.
- **No Secret Exposure**: SMTP passwords, private tokens, and internal server paths are never exposed in alert payloads.
